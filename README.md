# 电商支付反欺诈项目 Guide

这个项目模拟支付后的短窗审核。系统用交易发生时已知的信息估计欺诈风险，在有限的人工审核名额内选出待核查交易，再用回流标签评估策略。首版目标是在本地跑通数据、训练、评分、决策和监控，能从一笔交易的原始输入追溯到它为什么被送审。

核心实验比较两种排队方式：**同一个模型、同一批交易、相同审核名额，优先审欺诈概率最高的交易，还是优先审预计能挽回更多损失的交易？** 同时衡量欺诈笔数、金额和正常交易被送审的代价。这个对照是项目的主要成果，后续的行为序列和案件研判各自验证增量价值。

## 第 1–2 周 · 数据与模型基线

主数据使用 IEEE-CIS 的有标签训练交易与身份表，以 `TransactionID` 关联，用 `isFraud` 作为离线标签。`TransactionDT` 是相对时间。匿名卡片字段组合用作历史聚合的代理键，并记录代理键的缺失和覆盖率。原始比赛文件由复现者按规则获取，仓库提交数据说明和获取方式。 [IEEE-CIS 数据说明](https://www.kaggle.com/competitions/ieee-fraud-detection/data) · [比赛规则](https://www.kaggle.com/competitions/ieee-fraud-detection/rules)

1. **构建样本。** 按完整时间桶切出训练、校准、策略验证和最终测试四段，目标比例为 `60/10/10/20`。记录各段时间范围、笔数和正例率。编码、填补及规则分位点在训练段拟合，测试集留到模型和策略锁定后评估。
2. **挖掘特征。** 用 Python 和 DuckDB SQL 计算近 1 小时及 24 小时交易频次、历史金额均值、当前金额偏离和冷启动标记。窗口只读取严格早于当前交易的事件。身份字段先确认其预测时点可用性，缺失代理键按冷启动处理。
3. **建立对照。** 比较简单金额与频次规则、逻辑回归、LightGBM、XGBoost。对树模型做单笔特征与历史特征消融，抽查误报与漏报案例。保留验证 AP 表现最好的树模型作为候选，并报告线性基线的相同指标。

**进入下一周期的条件**是固定数据版本、切分和种子后能重跑结果。至少有一组时间窗口边界检查，以及一例能解释历史特征如何影响打分的错误分析。

## 第 3–4 周 · 审核策略、回放与监控

在校准段拟合概率校准器，在策略验证段确定固定误报率目标所用阈值，随后冻结阈值和策略参数。回放按相对时间分小时，桶结束时对刚结束的一桶交易分配审核名额，每小时默认两笔。未入队交易继续流转，入队交易进入人工复核演示。

- **同预算对照。** 第一组按校准后的欺诈概率排序。第二组按预期净收益排序，计算式为 `欺诈概率 × 金额 × 可挽回比例 − 单笔审核成本 − (1 − 欺诈概率) × 正常交易送审成本`。两组使用相同交易、概率和名额，同分按交易 ID 排序。用每小时一笔和四笔重跑，并对成本与可挽回比例做敏感性分析。
- **指标与成本。** 报告 AP、ROC-AUC、Brier 分数、验证阈值对应的测试 FPR 与召回、审核命中率、审核率及欺诈金额召回。成本回放从 80% 可挽回比例、1 单位审核成本和 2 单位正常交易送审成本开始。记录每组样本量、逐日波动及正常交易送审量，明确成本和损失是离线模拟估计。
- **服务与回流。** 用 FastAPI 提供本地评分接口，回放记录交易 ID、模型版本、分数、排序依据及入队结果。在模拟事件上设置 14 天标签延迟。标签成熟前监控输入缺失率、分数分布和审核量，成熟后再统计效果。打分失败时回退到基础规则，并在日志中标明。

**进入下一周期的条件**是能演示一笔交易从评分到标签回流，检查重复事件幂等、模型失败降级，以及批量与回放特征一致性，并保存两种策略的对照表和失败案例。即使价值排序在测试集上没有收益，也保留结果并解释原因。

## 第 5–6 周 · 行为序列

用 Fraud Detection Handbook 的模拟器构建带顾客、终端和事件时间的交易序列。模拟数据和 IEEE-CIS 各自报告，确保读者能区分仿真结论和公开比赛数据上的离线结论。 [交易模拟器](https://fraud-detection-handbook.github.io/fraud-detection-handbook/Chapter_3_GettingStarted/SimulatedDataset.html)

- 固定当前交易字段、历史窗口和时间划分，对比聚合特征 LightGBM、PyTorch GRU 和历史事件顺序被打乱的 GRU。
- 报告 AP、固定审核名额下的召回、推理耗时，并检查短序列与冷启动样本。图关系建模或 PySpark 特征复现放在序列实验完成后按需要追加。

**验收**是能用对照和至少一个失败案例解释模型是否利用了事件顺序，以及该收益是否值得额外的推理开销。

## 后续选做 · 本地案件研判

先做结构化证据卡，展示交易摘要、近窗行为、命中规则和待核查项。案件接口保留结论、证据 ID 与待核查项，由评分和审核策略负责支付处置。首版运行不需要外部模型 API。

有明确研判需求时，用 Ollama 接入本地 Qwen3-4B，比较模板证据卡、模型直接研判和模型查询只读证据后的结果。用同一批正常、可疑、证据缺失与证据冲突案例评测结论质量、有效引用率、正确弃答率和 p95 延迟。出现可重复的错误且已有经过校验的训练样本时，再考虑租卡做同基座 QLoRA，对比微调前后的质量、显存和耗时。 [Qwen 模型卡](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) · [Ollama 本地模型](https://ollama.com/library/qwen3%3A4b-instruct-2507-q4_K_M) · [PEFT 量化训练指南](https://huggingface.co/docs/peft/developer_guides/quantization)
